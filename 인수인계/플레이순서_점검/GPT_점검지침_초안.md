# 플레이 순서 점검 지침 (3판, 11-22 — GPT 검토 반영)

저장소 ygberserk/goei, 브랜치 `claude/project-thread-kd1w8j` (main = v0.21.32 와 같은 코드). RisuAI 플러그인 「괴이」.
이 글은 점검 방법이다. GPT 는 ① 이 방법에 빠진 것이 없는지, ② 점검 결과(나중에 이 폴더에 올라옴)가 맞는지를 본다. 코드를 직접 읽어도 된다.

---

## 1. 왜 이 점검을 하나

기존 시험(단위 1,200여 개)은 「코드가 짠 사람 생각대로 도는가」만 봤다. 실제로 한 판 하자 아래가 바로 나왔다. 모두 요청 글과 코드를 따라가면 보이는 것이었다.

| 나온 것 | 종류 |
|---|---|
| 상점에서 다 사고 새로고침하면 같은 물건이 또 나옴 (산 물건이 「다시 내지 말 것」 목록에서 빠짐) | 앞 단계 결과가 다음 요청 글에 안 들어감 |
| 호칭 낱말(예: 「선배」)로 엉뚱한 인물 기록이 생김 | 모델 답을 받아들이는 쪽이 너무 느슨함 |
| 인물 기록 0명인데 Router 가 도는 것처럼 표시 | 화면 표시와 실제 상태가 다름 |
| 망상홈쇼핑 상담원이 수락받고도 끊음 | 지침 글과 처리 코드가 서로 다른 말을 함 |
| 상점 값이 말이 안 됨 | 요청 글에 판단 근거가 모자람 |

이 다섯 종류가 다른 기능에도 있는지 찾는 것이 목표다.

## 2. 방법

기능 하나를 잡고 **플레이어가 실제로 누르는 단추에서 시작해** 끝까지 따라간다: 단추 → 모델 요청 → 답 처리 → 저장 상태 → 화면 → 다음 턴 본편 요청.

### 2-1. 두 겹으로 돈다
- **대표 경로**: 같은 판의 배포용 카드·플러그인·자료 팩(`npm run release:prep` 이 만드는 `.scratch/fixture/`)을 가짜 Risu(`tests/qc-settings-harness.mjs`·`tests/qc-host.mjs`, 실제 플러그인 번들을 브라우저에 띄움)에 넣고 화면 단추를 누른다. 기능마다 한 줄기.
- **갈래**: 같은 틀에서 상태만 바꿔 빠르게 돈다(설정 끔, 실패 답, 다시 굴리기 등). 브라우저로 전부 누르면 기능마다 몇 시간이 걸려서다.

### 2-2. 기록하는 자리 (고정)
- **보조 호출**: 가짜 Risu 의 `risuai.runLLMModel` — 첨부 처리(`withPhotos(prepareAttachments(...))`, `src/host/llm.ts`)가 끝난 실제 입력과 호출 횟수를 적고, 그 자리에서 가짜 답을 돌려준다.
- **본편 요청**: 등록된 `beforeRequest` 훅(`src/main.ts` → 본체 `beforeRequest`, `src/body.ts`)에 메시지를 넣고 돌아온 값을 적는다.
- **응답 처리**: `output` 리스너(본편 응답이 붙은 뒤 상점 표식·인물 기록·소지품 정리).
- 글이 어느 단계에서 빠졌는지는 이 세 자리를 비교해 짚는다.

### 2-3. 저장 위치 (기능마다 확인해 적는다)
- 상점·소지품·가계부·몰·망상홈쇼핑: `chat.scriptstate` (`$st_shop`, `$st_items`, 가계부 변수 등)
- 인물 기록: `chat.goeiPeopleV1` (scriptstate 밖, 값은 변경 기록에서 계산). 저장된 변경 기록과 **채팅을 다시 열었을 때 화면에 보이는 값**을 함께 본다.
- 그 밖의 기능은 점검할 때 코드에서 찾아 `찾은문제.md` 머리에 적는다.

### 2-4. 기대값을 먼저 적는다
단계마다 실행 **전에** 기대값을 적고, `run.mjs` 가 실제값과 자동 비교해 어긋난 단계를 짚는다. 요청 전문과 상태 파일은 근거로 남긴다. 기대값의 근거(사용자 결정·지침 글·위키)를 같이 적고, 근거가 없으면 정하지 않고 **사용자에게 물을 질문**으로 적는다.

### 2-5. 가짜 답으로 확정할 수 있는 것과 없는 것
- 확정 가능: 요청 글에 정보가 빠짐(예: 산 물건이 피할 목록에 없음), 지침과 코드가 다른 표식을 씀, 답을 잘못 처리함(수락 표식을 취소로), 상태·화면·다음 턴이 어긋남.
- 확정 불가: 값이 자연스러운지, 모델이 지침을 얼마나 자주 어기는지. 이건 실제 모델 응답을 본 범위에서만 말하고, 본 적 없으면 그렇다고 적는다.
- 가짜 답이 버그를 덮지 않게 한다: 예를 들어 새로고침에 가짜 답이 새 물건을 내면 피할 목록이 비어도 화면은 멀쩡하다. 그래서 **답을 돌려주기 전에 요청 글을 검사**한다.

실제 카드 자료(`카드/원본_봇카드.jpeg` 에서 `python3 -I tests/extract_module.py` 로 푸는 로어북 166개)를 쓴다. 장소·인물은 로어북에 있는 것만 쓴다.

## 3. 각 단계에서 묻는 것

**A. 요청 글**
- 판단에 필요한 정보, 지침의 우선순위, 허용되는 답 형식이 요청에 들어 있나? (지금 장면·시각·장소, 주인공, 앞에서 한 말, 이미 산 것, 정해진 값)
- 앞 단계에서 정해진 것이 이 글에 실제로 들어갔나? 지난 것이 지워져야 할 때 남아 있지 않나?
- 넣지 말아야 할 것이 들어갔나? (일부러 빼기로 한 잔고, 숨긴 진짜 효과, 다른 가게 것, 지난 턴 사건의 되풀이)
- 지침 절끼리, 지침과 처리 코드가 같은 표식·꼴·뜻을 쓰나?

**B. 답 처리**: 잘 쓴 답을 맞게 받나? 조금 틀린 답에서 엉뚱한 것을 받아들이지 않나(없던 인물·물건, 0원 값)? 못 받으면 무엇이 보이고 상태가 반쯤 저장되지 않나?

**C. 상태와 화면**: 화면이 상태와 같은 말을 하나? 결과가 다음 단계와 다음 턴 본편 요청에 들어가나?
- **한 번만 전달하는 것**: 사건(샀다·팔았다·주문했다·쫓겨났다·받았다)은 그 턴 본편에 한 번. 그다음 턴엔 사건으로 다시 나오면 안 된다.
- **계속 남는 것**: 산 물건은 그 뒤 턴마다 소지품 목록에 남는 게 정상. 이름이 몇 번 나오는지 세지 말고 「사건 줄」과 「목록 줄」을 나눠 본다.

**D. 순서·되풀이·되돌리기**: 연타, 순서 바꾸기, 답 기다리는 중 다른 단추, 본편 다시 굴리기·지우기, 창 닫았다 열기, 페이지 새로고침, 다른 채팅 갔다 오기. 끝에 **최종 잔고·수량·거래 건수**를 확인한다.
- 다시 굴리기의 기대값은 대상마다 따로 적는다: 그 응답에 묶인 거래(되돌아감), 수동 잔고 조정(그대로), 산 물건(진열대에 되살아남), 인물 기록 변화(되돌아감).

**E. 설정 갈래**: 기본값에서 바꾸면(켬·끔, 자동·수동, 컨텍스트 포함 끔, 개수 최소·최대) 요청 글과 동작이 설정대로 바뀌나? 설정이 코드에 박힌 값으로 덮이지 않나?

## 4. 모든 기능에 공통으로 넣는 갈래

| 갈래 | 보는 것 |
|---|---|
| 응답 실패 | 블록 빠짐·꼴 틀림·빈 답·시간 초과·재시도 뒤 성공. 내 말이 남나, 되돌려지나, 다시 보낼 수 있나 |
| 먼저 보낸 요청의 답이 나중에 도착 | 뒤 요청 답이 먼저 오고 앞 답이 늦게 와도 상태가 뒤집히지 않나 |
| 저장 실패 뒤 같은 행동 재시도 | 두 번 깎이거나 두 개 생기지 않나 (최종 잔고·수량·거래 건수) |
| 기다리는 동안 | 답 오기 전에 창 닫기·다른 단추·다른 채팅. 늦게 온 답이 엉뚱한 채팅·상태에 붙지 않나 |
| 본편 다시 굴리기 | 그 턴에 산 것·판 것·주문·기록이 같이 되돌아가나, 돈이 맞나, 다시 살 수 있나 |
| 본편 응답 지우기 | 위와 같음 |
| 다음 턴 | 결과가 본편 요청 글에 한 번만 들어가고 그다음 턴엔 안 들어가나 |
| 페이지 새로고침·채팅 다시 열기 | 저장 상태만으로 화면·다음 요청이 그대로 이어지나 |
| 설정 끔 | 끄면 요청 글에서도 빠지고 화면 카드도 안 뜨나, 켜면 돌아오나 |
| 컨텍스트 포함 끔·챗로그 턴 수·참조 로어북 수 | 요청 글이 설정대로 줄어드나 |
| 자동 호출 / 수동 | 자동이면 맞는 턴에 한 번만 도나, 다시 굴려도 또 안 도나, 수동이면 안 도나 |
| 보조 모델 / 메인 모델 선택 | 고른 모델로 가나 |
| PC / 폰 | 같은 동작이 두 배치에서 다 되나 (배치 모양은 다름이 정상) |

## 5. 기능별 순서

순서는 사용자가 정한 대로 1~5 를 먼저, 그 뒤 6~14.

### 1. 상점 (`src/core/shop.ts`, `shopctx.ts`, `shopfn.ts`, `src/ui/shop.ts`, 지침 `지침/상점.txt`)
1. 본편 응답에 `[shop: 가게|주인]` 표식이 붙음 → 카드 뜸 (표식 판단을 메인 모델이 할 때 / 갱신기가 할 때 / 주인공 자기 가게 / 고유 상점·인터넷 몰 이름)
2. 열기 → 첫 진열 요청(정체·주인 첫 말·진열대)
3. 물건 눌러 묻기 → 문의 요청
4. 흥정: 깎아 달라 / 다른 대가 제안 / 주인이 거절·역제안·수락 / 끊기(설정 켬·끔)
5. 없는 물건 찾기 → 들여옴(설정 「문의로 물건 바꾸기」 켬·끔) / 전부 바꿔 달라
6. 하나 사기 (잔고 충분·부족, 원이 아닌 대가, 희귀·특가)
7. 남은 것 다 사기 → 빈 진열대 화면
8. 본편 다음 턴 → 본편 요청 글에 산 것·나눈 말이 한 번
9. 같은 가게 표식이 다시 붙음 → 다시 열기 (상태 이어짐) / 표식이 안 붙음 → 상태 비움 / 다른 가게
10. 새로고침 → 다시 진열 요청(지난 진열·산 것 피하기, 이번 방문 대화 기억)
11. 팔기: 소지품 고름 → 값 묻기 → 흥정 → 「판매」 단추 / 말로 수락(`<deal/>`) / 주인이 안 삼 / 그만
12. 나가기 → 다음 턴 본편 요청 글
13. 포인트 상점(백일몽 소속일 때)과 원 상점의 차이

**상점에서 먼저 검증할 사례** (시작: 잔고 1,000원, 빈 소지품, 진열품 A 300원·B 200원, 구매 내역을 본편에 넘기는 설정 켬)
- ① 화면에서 A, B 를 차례로 산다 → 잔고 500원, 소지품 각 1개, 구매마다 거래 1건, 빈 진열대 안내.
- ② 빈 진열대에서 바로 새로고침 → 가짜 답을 돌려주기 **전에** 새로고침 요청의 「다시 내지 말 것」 목록에 A·B 가 둘 다 있는지 검사.
- ③ 다음 본편 요청과 그다음 턴 → 구매 사건은 한 번만, 소지품 목록엔 A·B 가 계속.
- ④ 따로: 사고 바로 다음 턴으로 넘어가 같은 가게를 다시 열고 새로고침 → ②와 비교해 다시 들어오는 과정에서 구매 이력이 사라지지 않나.

### 2. 우주 쇼핑몰 (`src/core/malls.ts`, `orders.ts`, `src/ui/malls.ts`, 지침 `우주쇼핑몰.txt`)
열기(자동 호출 기본 수동) → 진열(숨긴 진짜 효과·광고 문구, 진실 미리 정하기 설정) → 운영자 문의 → 정보 쪽지 사기 → 맞춤 주문 견적·선납 → 납기 지나 받기 → 사기·장바구니 → 받는 법(ARRIVE)이 본편에 → 팔기 → 다시 열기·새로고침 → 산 물건을 쓰는 턴에 진짜 효과가 본편에

### 3. 백일몽 포인트몰 (`src/core/malls.ts`, `points.ts`, `bmdesk.ts`, 지침 `백일몽포인트몰.txt`, `포인트몰_1대1상담.txt`)
백일몽 소속일 때만 → 열기 → 진열(포인트 값) → 사기(포인트 부족 포함) → 주문 조회·받으러 가기(PICKUP_TRY, 갈 수 없는 상황) → 받음 → 1:1 상담 → 다시 열기·새로고침. 다른 소속에서 포인트가 보이거나 쓰이지 않나

### 4. 망상홈쇼핑 (`src/core/homeshop.ts`, `hspeel.ts`, `hslog.ts`, `src/ui/homeshop.ts`, 지침 `망상홈쇼핑.txt`)
편성(자동 호출) → 방송 보기 → 내 채팅 보내기 → 진행자·시청자 반응 → 스티커 떼기 → 전화 걸기 → 상담원 첫 말 → 질문·흥정·맞교환 제안 → 말로 수락(`<deal/>`) / 단추로 주문 → 주문 뒤 상담원 말 → 끊기(수락 전·후, 상담원이 끊음·내가 끊음) → 다음 턴 상자 도착(ARRIVE) → 상자 열기 → 할부·방청 신청 턴 → 지난 주문 넘김 → 돈이 없을 때(가계부 끔)

### 5. 인물 기록 (`src/core/people/`, `src/host/people.ts`, 지침 `Router.txt`, `Director.txt`, `갱신기_*.txt`)
1. 기록 0명인 새 채팅 → 첫 턴 (Router·Director·갱신기가 도나, 화면 표시)
2. 새 인물이 이름과 함께 처음 나옴 → 갱신기가 기록 만듦
3. 이름 없이 호칭만 나옴(선배·아저씨·직원) → 기록이 생기면 안 됨
4. 같은 인물이 다른 호칭·별칭으로 나옴 → 같은 기록에 붙나
5. 명부(로어북) 인물 / 명부 밖 인물
6. Router 요청 → 장면 인물 고르기 → 본편에 들어가는 인물 글
7. Director 요청(설정 scene·facts·끔)
8. 매 턴 / 수동 갱신, 한 번에 읽는 응답 수
9. 오래 안 나온 인물, 기록 정리(consolidate)·줄이기(prune)
10. 호감·말투·관계 축 바뀜이 다음 턴 인물 글에

## 6. 남기는 것

기능마다 `인수인계/플레이순서_점검/<번호>_<기능>/` 아래:
- `run.mjs` — 단계를 차례로 돌려 요청 글·상태를 뽑고 기대값과 비교하는 스크립트. 2-1 의 가짜 Risu 위에서 돈다. 누구나 `npm run release:prep -- --skip-tests` 뒤 `node 인수인계/플레이순서_점검/<폴더>/run.mjs` 로 다시 돌릴 수 있게.
- `단계NN_<이름>.txt` — 그 단계 요청 글 전문과, 넣은 가짜 답
- `상태NN.json` — 그 단계 뒤 저장 상태
- `찾은문제.md` — 머리에 재현한 커밋·초기 설정·저장 위치. 문제마다: 누른 순서 / 기대값과 그 근거 / 실제값 / 플레이어에게 보인 증상 / 근거(파일:줄). 기대값을 정할 근거가 없으면 사용자에게 물을 질문으로. **고치기 전 목록**이다.

## 7. 진행 규칙

- 사용자 「최적의 형태로 진행 해」(11-22 21:15) 로 시작함.
- 기능 하나 끝나면 찾은 목록을 바로 올린다. 몰아서 올리지 않는다.
- 고치는 것은 목록을 사용자가 보고 「해」 한 뒤에만.
- 지침 글을 고칠 때는 하드코딩·메타 낱말 없이 평이하게. 사용자 설정·기본값을 코드로 덮지 않는다.
