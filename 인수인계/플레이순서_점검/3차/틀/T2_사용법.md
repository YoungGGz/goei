### 두 가지 네트워크 길 (`--via`)

- `plain` (기본): `db.usePlainFetch=true`. 브라우저가 가짜 서버로 바로 요청 → 스트리밍 조각이 실제로 조각으로 온다. 가짜 서버가 CORS 를 답한다.
- `proxy2`: `db.usePlainFetch=false` (실제 웹 사용자와 같음). 모델 요청이 `https://sv.risuai.xyz/proxy2`(`risu-url` 헤더)로 나가고, 조종 스크립트가 가로채 가짜 서버로 넘긴다. **이 길은 playwright `route.fulfill` 이 본문을 한 번에 넘겨 스트리밍 조각이 한 덩어리로 온다** (늦게 답하기·「만드는 중」은 그대로 됨).
- 받는 주소: 플러그인은 `risuFetch(plainFetchForce)`(직접)를 먼저 쓰고 실패하면 `nativeFetch`(/proxy2)로 받는다 (`src/host/datapack.ts`, `src/ui/update.ts`). 그래서 보통은 직접 길로만 받는다. `/proxy2` 길을 타게 하려면 `--release-direct fail`(또는 `t.setReleaseDirect('fail')`, 조종 서버 `{"op":"releaseDirect","v":"fail"}`)로 직접 받기를 끊는다. 두 길 모두 `/home/user/goei/release/` 로 돌린다.

## 틀을 돌리다 본 리스AI 쪽 동작 (판정 아님, 해당 구간에서 다시 본다)

1. **이어 쓰기**: 입력칸이 빈 채 메뉴 「이어 쓰기」를 누르면 리스AI `sendMain(true)` 가 `useSayNothing`(기본 켬)으로 마지막이 user 가 아니면 user `*says nothing*` 를 먼저 넣고 `sendChat(continue)` 한다 (`DefaultChatScreen.svelte:145-215`). 요청 끝에 system `[Continue the last response]` 가 붙는다(`index.svelte.ts:1228`). 붙는 자리는 스트리밍에 따라 다르다 (어느 쪽이든 메시지 수는 이어 쓰기 전보다 1 많고, 앞 메시지들은 그대로):
   - **스트리밍 켬**: 이어 쓴 글이 그 user 메시지 끝에 붙는다(`index.svelte.ts:1593-1599` msgIndex-1, prefix). 마지막 메시지가 **user** `*says nothing*T2 기본 본편 #N…`.
   - **스트리밍 끔**: 그 user 메시지 자리를 **char** `*says nothing*`+답 으로 바꾼다(`index.svelte.ts:1807-1830`). 마지막 메시지가 char `*says nothing*T2 기본 본편 #N…`, 화면에는 「*says nothing*」이 기울임으로 앞에 붙은 답 하나가 더 보인다.
   - check `(e)` 단계가 두 모드 모두 이 꼴(자리·role·메시지 +1·요청 1건·화면 글)을 판정한다. 리스AI 자체 동작이다(플러그인 없이도 같은 코드). `useSayNothing` 끔일 때는 갈래(E·H·I 「이어 쓰기」)에서 본다.
2. **첫 채팅 id**: 옛 틀은 캐릭터를 `selectedCharID.set` 으로만 골라 `characterFormatUpdate` 를 건너뛰어 첫 채팅 `chat.id` 가 비고 `fmIndex` 가 없었다(틀 탓). 실제 캐릭터 목록 단추 길 `changeChar` → `characterFormatUpdate`(`characters.ts:635-640`)가 id·fmIndex 를 채운다. 11-24 부터 틀이 `changeChar` 를 써서 setup 직후 chatId 가 있다(check `setup` 단계 `env.chatId`).
3. 보낼 때마다 리스AI 콘솔에 `TypeError: Cannot read properties of null (reading 'displayData')`. `request.ts:247-255` 가 `runTrigger(…,'request')` 결과의 `.displayData` 를 읽는데, `runTrigger` 는 캐릭터·모듈 트리거가 하나도 없으면 null 을 돌려준다(`triggers.ts:1090-1095`). 괴이 카드는 트리거가 0개(check `setup` 단계 `env.triggers`)라 늘 찍힌다. 리스AI 가 잡아서 넘기고 요청은 정상으로 나가며, 화면이 비는 것과는 상관없다(화면 빈 문제는 아래). 점검에서 오류 집계할 때 빼고 센다.
4. **시작 뒤 인사말 칸**: 출발 뒤 채팅 `fmIndex` 가 0 이 되고 다른 인사말 0번이 빈 글이라, idx -1 칸에 `.chattext` 없이 「Type something to start the chat.」와 ◀▶ 만 남는다(첫 장면은 메시지 0번). 의도인지는 해당 구간에서 본다(판정 밖, check 에 `greetBoxAfterStart` 로 기록만).

## 안 된 것·남은 제약

- 리스AI Node 서버 길(가)은 빌드가 필요해 쓰지 않았다(나 길로 다 됨).
- 보조 호출 스트리밍은 리스AI가 늘 끈 채 보내서 T2 로 못 닿는다(T1 몫, 코스 2-1).
- `newChat`·`switchChat` 은 채팅 목록 단추를 누르지 않고 같은 코드를 돈다. 옆 패널 단추를 실제로 눌러야 하는 갈래가 있으면 `[data-risu-chat-idx]` 단추로 바꿔 쓴다.
- 「새로고침 바로」(`reload({settle:false})`)와 늦은 답 중 새 채팅(번호 밀기)은 함수만 있고 0단계에서는 돌리지 않았다(공통 갈래 몫).
- 상태 파일(구간별 시작 상태)·결정표·T1 스위치는 이 일의 범위가 아니다.
- 여러 스레드가 같은 리스AI(5180)·조종 서버(7101)를 같이 쓰지 않는다(코스 8장). 다른 스레드는 `RISU_URL`·`--port` 를 바꿔 따로 띄운다. 가짜 서버는 `/_ctl/reset`·`rules` 가 모두에게 걸리니 스레드마다 `--port` 를 달리 띄우는 것이 안전하다.
